# Administration et API admin

L'admin répond en `npm run dev` (mode `local`, sans login) et sur la Preview Vercel de la branche `dev` (mode `remote`, login GitHub, voir `docs/admin-distant.md`). La production renvoie toujours 404 sur `/admin`.

- Modes : `src/lib/admin/auth/config.ts` (`resolveAdminAccessMode`). Le middleware vérifie la session (`authorizeAdminRequest`, `auth/access.ts`) et dépose le verdict dans `locals.adminAccess`.
- Toute nouvelle page `src/pages/admin/*.astro` exporte `export const prerender = false` et commence par `if (!isAdminGranted(Astro.locals)) return new Response('Not Found', { status: 404 });`.
- Toute nouvelle route `src/pages/api/admin/**` exporte `prerender = false` et appelle en premier, dans chaque handler, `const blocked = requireAdmin(locals); if (blocked) return blocked;` (`requireAdmin` de `src/lib/admin/shared.ts`). `src/lib/admin/auth/guards.test.ts` l'impose.
- Admin distant : refus par défaut. Une route n'y répond que si elle figure dans `src/lib/admin/remote-capabilities.ts`, ce qui suppose qu'elle lise par `getContentReader()` (`src/lib/admin/stores/content-reader.ts`, branche `dev` par l'API GitHub), écrive par `getContentWriter()` (`stores/content-writer.ts`, commit sur `dev`) et jamais directement sur le disque ni par `spawn`. Un enregistrement de contenu accepte la `revision` lue et répond 409 si elle est périmée (`toWriteErrorResponse`). `isLocalAdmin()` sépare les deux mondes : en local, disque et `spawn` ; à distance, images sur R2 par `src/lib/admin/remote-images.ts` (URL présignée puis `finalize`, jamais d'envoi multipart : 4,5 Mo maximum sur Vercel) et scripts dans GitHub Actions (`src/lib/admin/jobs.ts`, `.github/workflows/admin-job.yml`).
- Admin distant : le middleware plafonne (429 au-delà de 120 écritures par minute) puis journalise chaque écriture dans Turso (`src/lib/admin/audit-log.ts`). Le journal ne doit jamais faire échouer une action. La fusion de la PR de mise en production (`src/lib/admin/github/release.ts`) exige une CI entièrement verte et la tête affichée : ne pas assouplir ces conditions.
- WARNING: ne jamais affaiblir ces gardes. La production (`VERCEL_ENV=production`) doit rester `disabled` même si les variables de l'admin y sont définies (test dans `config.test.ts` et `middleware.test.ts`). Les routes écrivent sur le disque, sur R2 et dans Turso.
- Scripts `devOnly: true` dans `SCRIPTS` : lisent `src/assets/` ou `../astrobin`, ou sont destructifs ; ils ne seront jamais ouverts à distance. À distance, seules les entrées `remote: true` (opt-in, sans `devOnly` ni `needsTarget`, sans argument) tournent dans GitHub Actions ; un test (`scripts.test.ts`) l'impose et le runner `scripts/admin/run-admin-job.mjs` revérifie la liste blanche. `remoteOnly: true` (seules `update-photos-ci` et `update-photos-ci-force`, `update-photos.mjs --ci [--force-media]`) masque l'entrée en local et `api/admin/scripts/run.ts` la refuse : elle écrit sur le R2 de production et suppose un disque vide.
- Les requêtes inter-sites vers `/api/admin/**` et les POST inter-sites vers `/api/auth/**` (déconnexion) sont refusées (403). Le callback GitHub reste ouvert aux GET inter-sites (retour de GitHub), protégé par l'état signé et le PKCE. Contrôle par `src/middleware.ts` (`isCrossSiteRequest()`, `src/lib/admin/cross-site.ts`), y compris les GET consommés par EventSource. WARNING: ne pas retirer ni affaiblir ce contrôle.
- Scripts lancés depuis l'admin : les déclarer dans `SCRIPTS` (`src/lib/admin/scripts.ts`) avec `writes: true` s'ils modifient quelque chose. `api/admin/scripts/run.ts` les lance avec `spawn('node', args)` à la racine et diffuse la sortie en SSE. Les arguments passés en query sont transmis tels quels : ne jamais y ajouter de commande arbitraire.
- L'admin décide succès ou échec d'après le code de sortie. Un script exposé doit faire `process.exit(1)` en cas d'échec, pas `main().catch(console.error)`.
- `sync-r2` n'envoie que les fichiers absents de R2 (mode par défaut de `upload_local_to_r2.js`). Seule l'entrée `mirror-r2` (`--delete-first`, case « Delete first » de `R2Panel`) vide les préfixes distants ; un test (`scripts.test.ts`) l'impose.
- Les actions destructives côté UI passent par `ConfirmDialog.tsx`.
- Domaines séparés : chaque bouton porte sur un seul domaine (astrophotos, blog ou voyages), et les pages d'un domaine n'agissent que sur lui. Un script partagé reçoit `--only` (`generate-mini.mjs`, `generate-web-images.mjs`) ou un dossier (scripts `r2/`). Une entrée de `SCRIPTS` sans cible figée porte `needsTarget: true`, ce qui la masque de `/admin/scripts` ; un test (`scripts.test.ts`) l'impose. Les pages R2 et Cache n'ont plus d'option « tous les répertoires ». Mise à jour d'un domaine : `AstroPhotosPanel.tsx` (`update-photos`) et `ContentUpdatePanel.tsx` (`update-blog`, `update-voyages`).
- `WebImagesReminder.tsx` est un îlot autonome (ses propres `AdminProviders`) monté en tête de plusieurs pages admin : il signale les images sans versions web et lance l'entrée `generate-web-images` de `SCRIPTS`. Avec `scope`, il se limite au domaine de la page ; sans `scope` (tableau de bord, R2), il affiche un bouton par domaine.
- Fichiers de contenu : passer par les helpers de `src/lib/admin/blog-files.ts` et `voyages-files.ts` (miniatures, frontmatter), bâtis sur `content-files.ts` (chemins `<année>/<slug>`, liste, suppression, enregistrement d'image). Validation et chemins : `validateYear`/`validateSlug`/`validateFilename` et `safeResolve()` de `shared.ts`, jamais `path.join` sur une entrée utilisateur. Réponses JSON : `jsonResponse()` de `shared.ts`. Le `.360-manifest.json` n'existe que pour le blog (`mark360Image()` dans `blog-files.ts`).
- Images uploadées : `compressImage()` (`src/lib/admin/image-process.ts`) produit le full en 2400 px q82 et le `-thumb.jpg` en 800 px q60. La synchronisation R2 passe par `syncDirToR2()` (`src/lib/admin/r2-sync.ts`).
- Voyages : les images supprimées vont dans `.admin-trash/` (git-ignoré, `voyages-files.ts`). Cela évite que le watcher Vite lève `ImageNotFound` entre la réécriture du markdown et la suppression du fichier. Blog : `deleteImage` supprime directement le fichier et sa miniature (`unlink`).
- Le CSV des astrophotos (`data/astrobin_clodoweg_gallery_python.csv`) n'est écrit que par le scrape AstroBin. Ne jamais ajouter d'édition du CSV dans l'admin, locale ou distante : `updatePhotoMetadata` (`astrophotos.ts`) n'écrit que `alt.json`, les fiches Wikipedia et techniques, `seo.json` et `drafts.json`.
- L'admin ne génère ni alt ni description SEO. `/admin/astrophotos`, `/admin/blog`, `/admin/voyages` et `/admin/seo` indiquent ce qui manque et renvoient vers Claude Code (`ClaudeCodeNotice.tsx`, `/generate-alts`, `/generate-seo`). Astrophotos : l'alt se construit depuis le CSV. L'éditeur de blog reprend seulement les alts connus de `alt.json`. `/api/admin/content-gaps` (`src/lib/admin/content-gaps.mjs`) calcule les manques du blog et des voyages.
- Éditeurs : les parties communes au blog et aux voyages vivent dans `src/components/Admin/editor/` (`Field`, `StatCard`, `EditorSidebar`, `preview.ts`, `useSidebarCollapsed`, `withAdminProviders`). Les réutiliser plutôt que les recopier dans `BlogEditor.tsx` ou `VoyagesEditor.tsx`.
- Corps des articles : éditeur WYSIWYG `editor/rich/RichMarkdownEditor.tsx` (Tiptap), dont la valeur reste du Markdown. Toute conversion passe par `markdown-bridge.ts`, qui réécrit à l'identique les blocs non modifiés : un nouveau nœud doit y avoir son parse et sa sérialisation, et `markdown-bridge.test.ts` (aller-retour sur tous les articles de `src/content/`) doit rester vert. Le schéma est dans `nodes.ts` + `extensions.ts`, sans React, pour rester testable. Les métadonnées s'éditent dans `editor/SettingsDrawer.tsx` ; brouillon local, Ctrl+S et aperçu réel (`openArticlePreview.ts` → `/api/admin/preview` → `/admin/apercu`) sont communs aux deux éditeurs.
- Aperçu réel : `src/lib/admin/article-preview.ts` doit garder les plugins rehype dans l'ordre d'`astro.config.mjs` (test dédié). Une image seule suivie d'un paragraphe n'a pas de légende sur le site (masonry en fait un `<picture>` avant `rehype-figure`) : l'éditeur ne doit pas en afficher.
- Tests : `BlogEditor.test.tsx` et `LighthousePanel.test.tsx` mockent `global.fetch`. `blog-files.test.ts` mocke `node:fs` et `sharp`. Les tests de routes de `src/pages/api/admin/` sont préfixés `_` (`_seo.test.ts`). Suivre ces modèles.
